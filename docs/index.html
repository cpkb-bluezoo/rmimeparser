rmimeparser

Push-based MIME and RFC 5322 parsing and writing in Rust— constant memory, no message DOM, stdlib only.

Overview

rmimeparser never builds a tree of parts. Instead you implement a handler whose methods the parser calls as structure and content are recognised. The writer is the inverse: you call the same style of event methods, and encoded wire bytes stream into any std::io::Write.

  • MimeParser + MimeHandler — MIME entities, CTE decoding, multipart
  • MessageParser + MessageHandler — RFC 5322 headers on top of MIME
  • DkimMessageParser — same typed handler API, plus wire-byte accessors for DKIM
  • MimeWriter / MessageWriter — safe serialization (folding, CTE, RFC 2047)

Implementing a handler

All MimeHandler methods have default no-op bodies. Override only what you need. Return Err(...) from a callback to abort parsing.

Minimal example

use loopbuf::LoopBuf;
use rmimeparser::{MimeHandler, MimeParser, ParseResult};

struct CountBody {
    bytes: usize,
}

impl MimeHandler for CountBody {
    fn body_content(&mut self, data: &[u8]) -> ParseResult<()> {
        self.bytes += data.len();
        Ok(())
    }
}

let raw = b"Content-Type: text/plain\r\n\r\nHello\r\n";
let mut parser = MimeParser::new(CountBody { bytes: 0 });
let mut ring = LoopBuf::with_capacity(8192);
ring.extend_from_slice(raw);
parser.receive(&mut ring)?;
parser.close(&mut ring)?;
assert_eq!(parser.handler().bytes, 7);

Callback order

For a simple (non-multipart) entity the parser drives your handler roughly like this: 

set_locator(...)
start_entity(None)
  header callbacks: start_content_type … end_content_type (parameters between)
    and the other MIME headers; start_header, header_content*, end_header for the rest
    start_header, header_content*, end_header for every other header
  end_headers()
  body_content(...)       // transfer-decoded octets (may be chunked)
end_entity(None)          // from close()
CallbackWhen
set_locator Once at start; locator tracks offset / line / column for errors.
start_entity Root: None. Multipart part: Some(boundary) when that part begins.
start_header / header_content / end_header Every header the parser does not itself understand, unknown ones included: its value as unstructured text, in pieces of no particular size, unfolded and trimmed, RFC 2047 encoded words decoded. The parser does not hold the value.
header_delivery Asked once per such header, just before start_header. A layer that parses some headers itself (MessageParser does) answers HeaderDelivery::Raw and gets the value as raw_header_content(&[u8]): undecoded, only unfolded.
start_content_type / end_content_type Content-Type: the type and subtype, then its parameters, then the end. Content-Disposition likewise (start_content_disposition). Nothing is held but the head; a parameter value of any size streams.
start_parameter / parameter_content / end_parameter One parameter, its value decoded and in pieces of no particular size: quoted-pairs, RFC 2047 words and RFC 2231 (name*=, and continuations name*0, name*1 joined in order) all resolved. language is Some for an extended value, so a handler can prefer filename* to filename.
malformed_header The head of a Content-Type / Content-Disposition is not valid. Stands in for start_header: the whole value follows as unstructured text, header_content then end_header.
content_transfer_encoding, content_id, mime_version The other headers the parser understands: short values, delivered whole.
end_headers Blank line after headers; body (or first multipart boundary) follows.
body_content Transfer-decoded body octets. May arrive in several calls—do not assume one shot. Charset decoding of text parts is left to you (see Content-Type charset).
unexpected_content Preamble/epilogue-like content where a boundary was expected.
end_entity Entity finished; multipart close uses Some(boundary).
Always prefer these typed callbacks. They deliver decoded strings and structured values. Wire-accurate capture for DKIM is a separate entry point—see DKIM / raw wire.

Feeding the parser with bytes

Call receive(&mut ring) repeatedly with a caller-owned loopbuf::LoopBuf. The parser consumes what it can use and leaves the rest in the ring. Header lines are parsed whole, so what is left in the ring is an incomplete header line (underflow)—add the next read after it. Body bytes are consumed as they arrive and delivered as zero-copy runs, so a body is never left in the ring and needs no buffering on your side, whatever its line lengths.

Streaming buffer loop

use loopbuf::LoopBuf;
use rmimeparser::{MimeHandler, MimeParser, ParseError, ParseResult};

fn parse_stream<R: std::io::Read, H: MimeHandler>(
    mut reader: R,
    handler: H,
) -> ParseResult<H> {
    let mut parser = MimeParser::new(handler);
    let mut ring = LoopBuf::with_capacity(8192);

    loop {
        let (spare, _) = ring.spare_capacity_mut();
        let n = reader
            .read(spare)
            .map_err(|e| ParseError::new(e.to_string()))?;
        if n == 0 {
            break;
        }
        ring.commit_write(n);
        // What the parser cannot use yet is still in the ring.
        parser.receive(&mut ring)?;
    }

    parser.close(&mut ring)?;
    Ok(parser.into_handler())
}

// Or let the parser do exactly that:
//     MimeParser::new(handler).parse(reader)?;
  • After receive, if parser.is_underflow() is true, more input is needed before the current header line, or the current line of a multipart body, is complete (a multipart line that might be a boundary, at most about 76 bytes, is the only body data the parser holds back). A header line longer than ParserLimits::max_header_line_length (998) is rejected as soon as that length is exceeded, without waiting for its terminator; a ring full of one unfinished line is an error, because it can never fit.
  • close(&mut ring) parses what the ring still holds first, so a final line with no terminator is delivered as a header, as body content or as the closing boundary. It fails if a multipart body is left unclosed.
  • You can also feed the entire message in one receive if it already sits in the ring.
  • The parser owns its handler: handler(), handler_mut() and into_handler() get at it, and MimeParser::new(&mut handler) lends one you want to keep.
The ring is yours and the parser never grows it. It has to be able to hold the longest header line (998 bytes plus its terminator).

RFC 5322 message parser

MessageParser wraps MimeParser; MessageHandler extends MimeHandler. The MIME layer knows nothing of RFC 5322, so anything that needs only MIME (HTTP’s multipart/form-data, say) uses MimeParser alone. Implement MessageHandler to get typed address, date, and Message-ID headers in addition to the MIME callbacks. 

use loopbuf::LoopBuf;
use rmimeparser::{MessageHandler, MessageParser, ParseResult};

struct CollectSubject {
    subject: Option<String>,
    in_subject: bool,
}

// A header the parser does not parse arrives as unstructured text in pieces.
impl rmimeparser::MimeHandler for CollectSubject {
    fn start_header(&mut self, name: &str) -> ParseResult<()> {
        self.in_subject = name.eq_ignore_ascii_case("subject");
        Ok(())
    }
    fn header_content(&mut self, text: &str) -> ParseResult<()> {
        if self.in_subject {
            self.subject.get_or_insert_with(String::new).push_str(text);
        }
        Ok(())
    }
}

impl MessageHandler for CollectSubject {}

let raw = b"Subject: hello\r\n\r\nHi\r\n";
let mut parser = MessageParser::new(CollectSubject { subject: None, in_subject: false });
let mut ring = LoopBuf::with_capacity(8192);
ring.extend_from_slice(raw);
parser.receive(&mut ring)?;
parser.close(&mut ring)?;
CallbackTypical headers
start_header / header_content / end_header Every other header, unknown ones included, as unstructured text (these are MimeHandler events): Subject, Comments, Received, X-…, …
start_address_header / mailbox / start_group / end_group / end_address_header From, To, Cc, Reply-To, …: one mailbox(display_name, local, domain) per address, as it is read; nothing but one address is held, so a list of any length streams. Groups are groups.
start_message_id_header / message_id / end_message_id_header Message-ID, In-Reply-To, References, …: an id at a time.
date_header Date, Resent-Date, …
obsolete_structure Once for a header, before the first event an obsolete syntax affected.
malformed_header An element could not be read (a MimeHandler event). What came before has been delivered; the rest of the header, from that element, follows as unstructured text.

DKIM / raw wire capture

DKIM canonicalization needs the message exactly as received (folded header bytes, undecoded body lines). That is intentionally not exposed on MimeHandler / MessageHandler.

Use DkimMessageParser instead of MessageParser. You still implement the same typed MessageHandler for decoded events. After receive / close, read wire data from the parser: 

use loopbuf::LoopBuf;
use rmimeparser::{DkimMessageParser, MessageHandler, MimeHandler, ParseResult};

struct App;
impl MimeHandler for App {}
impl MessageHandler for App {}

let mut parser = DkimMessageParser::new(App);
let mut ring = LoopBuf::with_capacity(8192);
ring.extend_from_slice(raw);
parser.receive(&mut ring)?;
parser.close(&mut ring)?;

// Decoded events already went to the handler.
// Wire bytes for DKIM:
let headers = parser.raw_headers();      // &[RawHeader], folds preserved
let body = parser.raw_body();            // undecoded body lines
let from = parser.raw_header("from");    // Option<&RawHeader>
Everyday apps should keep using MessageParser. Reach for DkimMessageParser only when you need canonicalization input.

Using the writer

MimeWriter and MessageWriter are push APIs—no builder or in-memory message tree. You emit events; the writer folds headers, applies RFC 2047 where needed, and CTE-encodes body chunks as they arrive. They write into a caller-owned loopbuf::LoopBuf and hold none of the output; working memory is one call's worth of scratch and the encoder state.

Every call is atomic: it appends everything it was asked to or nothing, and leaves the writer as it was. A WriteError says why it failed. is_would_block() means the ring has no room right now: drain it and repeat the same call. ErrorKind::InvalidInput means the call can never succeed: it needs more room than the whole ring has, it is not valid in the writer’s state (a body before end_headers), or what it was given is not valid MIME (a bare CR in a 7bit body, a body that contains the multipart boundary).

Single part

use loopbuf::LoopBuf;
use rmimeparser::{ContentType, MimeWriter};

let mut ring = LoopBuf::with_capacity(8192);
let mut w = MimeWriter::new();

w.start_entity(&mut ring, None)?;
w.content_type(&mut ring, &ContentType::new("text", "plain", None))?;
w.content_transfer_encoding(&mut ring, "base64")?;
w.end_headers(&mut ring)?;

// Logical body octets — call as many times as you like. It returns how many it
// took: as many as fit in the ring, so loop until the rest has gone in.
let mut rest: &[u8] = b"Hello world";
while !rest.is_empty() {
    match w.body_content(&mut ring, rest) {
        Ok(taken) => rest = &rest[taken..],
        Err(e) if e.is_would_block() => { /* write the ring out to the socket, then retry */ }
        Err(e) => return Err(e.into()),
    }
}

w.end_entity(&mut ring, None)?;
w.close()?;
  • Declare Content-Transfer-Encoding before end_headers. Default is 7bit.
  • body_content takes logical bytes; the writer encodes to base64 / quoted-printable when those CTEs are set. For 7bit, high bytes and NULs are rejected.
  • Finish every open entity with matching end_entity, then close(), which writes nothing and so takes no ring. reset() readies the writer for another message.

Advanced: header_raw_value / writer raw_header / raw_body_content exist to emit already-encoded wire bytes. Prefer the typed writer methods for normal construction.

RFC 5322 message writer

use loopbuf::LoopBuf;
use rmimeparser::{
    ContentType, EmailAddress, MessageWriter, OffsetDateTime,
};

let mut ring = LoopBuf::with_capacity(8192);
let mut w = MessageWriter::new();

w.start_entity(&mut ring, None)?;
w.header(&mut ring, "Subject", "Café")?;           // RFC 2047 as needed
w.date_header(&mut ring, "Date", OffsetDateTime::new(2024, 6, 15, 12, 0, 0, 0))?;
w.address_header(&mut ring, 
    "From",
    &[EmailAddress::new(Some("Ada".into()), "ada", "example.com", false)],
)?;
w.content_type(&mut ring, &ContentType::new("text", "plain", None))?;
w.content_transfer_encoding(&mut ring, "quoted-printable")?;
w.end_headers(&mut ring)?;
w.body_content(&mut ring, "Hello café".as_bytes())?; // returns how many bytes it took
w.end_entity(&mut ring, None)?;
w.close()?;

Multipart (parse and write)

On parse, each part is a nested start_entity(Some(boundary)) … end_entity(Some(boundary)) sequence after the parent’s end_headers.

On write, mirror that structure:

use loopbuf::LoopBuf;
use rmimeparser::{ContentType, MimeVersion, MimeWriter, Parameter};

let mut ring = LoopBuf::with_capacity(8192);
let mut w = MimeWriter::new();

w.start_entity(&mut ring, None)?;
w.mime_version(&mut ring, MimeVersion::V1_0)?;
w.content_type(&mut ring, &ContentType::new(
    "multipart",
    "mixed",
    Some(vec![Parameter::new("boundary", "bound123")]),
))?;
w.end_headers(&mut ring)?;

w.start_entity(&mut ring, Some("bound123"))?;
w.content_type(&mut ring, &ContentType::new("text", "plain", None))?;
w.end_headers(&mut ring)?;
w.body_content(&mut ring, b"Part one")?;
w.end_entity(&mut ring, Some("bound123"))?;

w.start_entity(&mut ring, Some("bound123"))?;
w.content_type(&mut ring, &ContentType::new("text", "plain", None))?;
w.end_headers(&mut ring)?;
w.body_content(&mut ring, b"Part two")?;
w.end_entity(&mut ring, Some("bound123"))?;

w.end_entity(&mut ring, None)?; // emits --bound123--
w.close()?;
The writer refuses body_content that would embed the active multipart boundary (\r\n--boundary). Prefer base64 for binary parts under multipart.

Transfer encodings

The parser decodes Content-Transfer-Encoding bodies as the bytes arrive, so body_content always carries logical bytes: base64, quoted-printable and uuencode (x-uuencode, x-uue, uuencode, uue). Each codec is also a standalone push decoder with one calling convention: decode_base64, decode_quoted_printable and decode_uuencode take (src: &mut &[u8], dst: &mut Vec<u8>, max, end_of_stream), consume as much of src as they can turn into at most max output bytes, and leave an incomplete trailing unit (a base64 quantum, a soft line break, a uuencode line) in src for the next call unless end_of_stream is set. The Base64Decoder, QuotedPrintableDecoder and UuencodeDecoder types are the same functions behind a name, with estimate_decoded_size for sizing the output.

The encoders stream too: Base64Encoder, QuotedPrintableEncoder and UuencodeEncoder take write(out, data) (any std::io::Write, returning io::Result) in any chunking and finish(out), holding at most one partial unit; encode_base64, encode_quoted_printable and encode_uuencode(out, filename, mode, data) do a whole buffer in one call. uuencode's begin line is written on the first write, the "`" and end lines by finish. MimeWriter drives the base64 and quoted-printable encoders itself; a uuencode body needs the filename for its begin line, so it is written with raw_body_content from UuencodeEncoder output.

Errors and limits

  • Parse failures use ParseError / ParseResult; the message says where in the message it was found. A handler callback returns the same ParseResult, and an error from it stops the parse.
  • Write failures use WriteError / WriteResult, the same type the other writers built on LoopBuf return.
  • Limits are one struct, ParserLimits (None is no limit), set with with_limits, limits_mut or set_limits: max_element_length (default 4 KiB: what is held to judge, an address at a time) and max_header_line_length (default 998 octets). set_chunk_size bounds the body bytes handed to the handler at a time and set_buffer_size sizes the ring parse(reader) allocates.
